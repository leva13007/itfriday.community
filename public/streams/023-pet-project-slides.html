Чому власний застосунок, який працює в інтернеті, — найкоротший шлях пройти повний життєвий цикл продукту

Що це

Що таке pet-проєкт

Застосунок, який ви робите з власної ініціативи, для себе або невеликої аудиторії, і за який відповідаєте повністю — від першого коміту до сервера, що має працювати вночі.

Навіщо

Навіщо розробнику pet-проєкти

01

Нові технології

На роботі стек фіксований. У pet-проєкті можна спробувати Go, Rust, Svelte, Postgres замість MySQL — без ризику для бізнесу

02

Свобода рішень

Ніхто не каже «так історично склалося». Ви самі обираєте архітектуру, бібліотеки й спосіб деплою — і самі живете з наслідками

03

Інженерне мислення

Немає тімліда, який приймає рішення за вас. Доводиться самому зважувати компроміси, читати документацію, розбиратися з помилками

04

Портфоліо

Посилання на робочий застосунок переконує краще за будь-який рядок у резюме. Код у GitHub показує, як ви думаєте

Головне: pet-проєкт — єдине місце, де junior проходить увесь цикл, а не лише свій тікет.

Дискусійне питання

Чи має pet-проєкт приносити прибуток?

«Так, інакше він помре»

  • Гроші — найчесніша перевірка, що проблема справжня
  • Навіть $5 на місяць за сервер мотивують не закинути
  • Платні користувачі дають вимоги, яких не вигадаєш сам
  • Indie hacking, SaaS на одну людину — реальна кар'єрна траєкторія

«Ні, прибуток вбиває свободу»

  • Щойно є клієнти — зникає право експериментувати зі стеком
  • Підтримка, рахунки, GDPR, податки замість нових технологій
  • Більшість ідей не монетизуються, і це нормально
  • Мета — досвід; продукт є побічним ефектом

Компроміс: ставте ціль «один справжній користувач, який не ви», а не «перший долар». Гроші прийдуть або ні — досвід залишиться.

Ідея

Як обрати ідею для pet-проєкту

Не починайте з великого

«Своя соцмережа», «аналог Notion», «маркетплейс» — це роки роботи команди. 90% таких проєктів закінчуються на екрані логіну.

Вирішуйте конкретну проблему

Краще свою: вам не треба проводити дослідження користувачів — ви і є користувач. Біль, який ви відчуваєте щотижня, — найкраще ТЗ.

Визначте MVP

Одна функція, яка вже приносить користь. Усе інше — у список «потім». Якщо MVP не можна зробити за кілька вихідних — він ще не MVP.

Production

Реальні користувачі приносять реальні проблеми

  • Хтось вставив емодзі в поле, де ви чекали число
  • Файл на 200 МБ там, де ви тестували на 2 КБ
  • Сервер упав о третій ночі, а дізналися ви вдень із повідомлення в Telegram
  • Міграція зламала таблицю, а бекапу немає
  • Через місяць диск заповнили логи
  • Домен прострочився, бо автоплатіж не пройшов

Чому це добре

Кожна з цих проблем — тема, яку junior у компанії бачить лише з боку: нею займаються DevOps, SRE або сеньйор. У pet-проєкті вона ваша, і ви розумієте її не з лекції, а з ночі, коли все впало.

Саме тут народжується «розуміння системи в цілому», про яке йшлося в попередній доповіді.

Деплой

Три шляхи деплою pet-проєкту

Класичний: shared hosting

cPanel-хостинг за $2–5. PHP (Laravel, WordPress) і статика: файли по FTP або з Git, MySQL уже є, SSL — кнопкою. Деплой за годину.

Простий: PaaS

Railway, Render, Vercel, Fly.io. Підключаєте GitHub-репозиторій — платформа сама збирає, запускає, видає HTTPS-адресу. Деплой за 15 хвилин.

Просунутий: VPS + Docker

Hetzner, DigitalOcean + Docker Compose + Nginx або Traefik. Сервер, домен, сертифікати, бекапи — самі. Деплой за вихідні, але ви розумієте кожен шар.

Практичний deployment: шість кроків

1

Сервер

VPS на Ubuntu, SSH за ключем, ufw відкриває лише 22, 80, 443

2

Домен

A-запис на IP сервера. Поки DNS оновлюється — ставимо Docker

3

Docker Compose

Проксі, застосунок, база — три сервіси в одному файлі

4

Env variables

Секрети в .env на сервері, ніколи в репозиторії

5

HTTPS

Caddy або Traefik отримують сертифікат Let's Encrypt автоматично

6

Запуск

docker compose up -d, міграції, перевірка з телефона

Кожен крок окремо — година роботи. Разом — перший застосунок, який працює без вашого ноутбука.

Експлуатація

Деплой — не фініш. Що потрібно після нього

Logs

Логи

docker compose logs -f — спочатку досить. Далі — Loki або Better Stack, щоб шукати по всіх контейнерах і не забивати диск

Monitoring

Моніторинг

Uptime Kuma або Better Uptime пінгують сайт щохвилини і пишуть у Telegram, коли він упав. Ви дізнаєтесь раніше за користувачів

Backup

Бекапи

pg_dump щоночі в S3-сумісне сховище. Бекап, який жодного разу не відновлювали, — це не бекап

Security

Безпека

Оновлення ОС, fail2ban, закриті порти, HTTPS, rate limit на логін, залежності без відомих CVE

Updates

Оновлення і відкат

Теги образів замість latest: тоді відкат — це запуск попередньої версії, а не паніка

Перший місяць після запуску вчить більше, ніж три місяці написання коду до нього.

Досвід

Що pet-проєкт дає розробнику

Повний життєвий цикл

Ідея, вимоги, архітектура, код, тести, деплой, підтримка — усі етапи SDLC своїми руками, а не один тікет із середини

DevOps та інфраструктура

Docker, Linux, DNS, TLS, CI/CD перестають бути словами з вакансій і стають речами, які ви налаштовували о другій ночі

System Design на практиці

Чому моноліт, де кеш, що буде під навантаженням, як не втратити дані — відповіді з власного досвіду, а не з відео

Висновок

Шлях pet-проєкту

Idea→ Code→ Production→ Users→ Problems→ Experience
  • Без production немає users, без users немає problems, без problems немає experience
  • Більшість pet-проєктів зупиняються на кроці Code — і втрачають чотири кроки з шести
  • Маленький застосунок, який живе в інтернеті, цінніший за великий, який живе на localhost
Висновок

Pet-проєкт стає досвідом не тоді, коли написано код, а тоді, коли ним користується хтось інший, щось ламається і ви це лагодите.
